一句话定位

Graph Engineering 不是又一个 Prompt 包装器，而是 AI Coding Agent 之上的自动化开发控制层：它把“模型需要推理的工作”和“系统必须可靠的控制”彻底分离。

面试口径：传统 Agent 解决“怎么写代码”；Graph Engineering 解决“怎么让一条包含需求、实现、验证、审查和交付的长流水线可恢复、可审计、可叫停”。

为什么要做

需求会丢

一次长会话 compact 或切换 Agent 后，需求和验收标准容易只存在于上下文中。

对策：HumanMessage、TaskContract、acceptance lock 持久化且 append-only。

角色会混

同一个 Agent 既写代码又验证又审查，容易把错误实现解释成成功。

对策：Implementer / Verifier / Reviewer / Observer Session 与权限隔离。

失败难恢复

代码失败、CI 故障、网络超时和外部副作用不确定不能用同一种重试。

对策：failed/error 分类、checkpoint、幂等键、barrier 和 Final Report。

人机难共存

Human 查进度不应打断 Agent；发现方向错误又必须能立即暂停、修订。

对策：独立 Observer、Human Gateway、Control Intent 和执行屏障。

三分钟项目讲述稿

我做的是 Graph Engineering，一个面向 AI Coding 的自动化开发控制层。它不是让模型单次生成代码，而是把一次需求实现拆成需求探索、方案设计、编码、测试验证、独立审查和成果交付六个阶段，并用持久化执行图组织它们。

系统入口是 Human Control Conversation。Human 用自然语言描述需求、验收标准和权限边界；消息先作为不可变 HumanMessage 落库，再由 Intent Compiler 编译成受限的 Control Intent。Discovery 扫描仓库并澄清缺失信息，生成 TaskContract。只有 Human 明确确认，Contract、Verifier 和 acceptance lock 才会冻结，Runtime 才准备 Run。

执行时，Implementer 在隔离 Git worktree 中编码，Verifier 运行确定性测试，Reviewer 用全新的只读 Session 检查 Contract、diff 和证据，Observer 独立读取进度。GraphRuntime 根据结果路由：测试失败进入有预算的 repair，审查发现问题进入 review-fix 后重新验证，基础设施异常则重试或终止。

系统的核心不是调用模型，而是控制不变量：状态在 SQLite，事件和产物可追溯，外部副作用有 checkpoint 和幂等键，pause/interrupt 先建立 barrier，所有终态都生成 Final Report。Human 最后 accept、reject 或 revise，accept 只记录验收，默认不会自动合并。

阶段时间线

Start：先保存，再解释

创建或恢复 Conversation，追加带 actor/project/run identity 的 HumanMessage。重复 message_id 幂等，内容冲突拒绝。

Discovery：从仓库事实开始

ProjectScanner 使用 Git 文件清单并限制规模；固定澄清 verification、acceptance、dependencies、conventions、permissions、delivery、budget，形成 Contract draft。

Freeze：需求成为不可变事实

Human confirm 后生成 frozen Contract、acceptance lock 和 Verifier binding。方向变化不覆盖旧版本，而是产生 delta、revision 和 successor Run。

Prepare：准备不等于执行

RunPlanner 校验 hash，Compiler 把 Contract 转成 ExecutionGraph，写入 prepared Run。此时不会静默启动 Agent、网络或 GitHub 副作用。

Execute：受控反馈闭环

GraphRuntime 恢复 checkpoint，按节点/边/预算调度；实现、验证、修复、审查、审查修复和交付都写入持久状态。

Deliver：以证据交给 Human

Final Report 从 SQLite、Event、Artifact、Git 和 Review 事实编译，包含 changed files、测试、CI、审查、成本、未验证项和 residual effects。

三层概念

Harness Engineering

给单个 Agent 正确的上下文、工具、权限、工作目录和输出 schema。

Loop Engineering

用测试、审查、失败反馈和预算让局部任务收敛。

Graph Engineering

把多个 Agent、工具、外部系统和 Human 边界组织为可组合、可恢复、可审计的执行图。

五类事实源

  • 需求事实：冻结 Contract
  • 状态事实：SQLite StateStore
  • 事件事实：追加式 JSONL EventStore
  • 证据事实：内容寻址 ArtifactStore
  • 代码事实：Git branch/worktree

模型上下文是临时缓存，不是任何一类权威事实源。

核心机制：为什么它不会“失控”

1. 推理与控制分离

Agent 可以提出方案、写代码、解释 diff；但不能直接改变 Run 状态、Contract、Verifier 或预算。

2. Contract 冻结

acceptance criteria、权限、Verifier、delivery policy 冻结并 hash 绑定。修订只能创建新版本。

3. 状态机持久化

Run、Node、Attempt、Session、Checkpoint 和 External Handle 写入 SQLite，进程重启不依赖对话记忆。

4. 角色隔离

Implementer 可写；Verifier 按声明执行；Reviewer/Observer 只读且使用 fresh Session。

5. Fail closed

歧义、权限缺失、输入漂移、未知副作用、超预算和外部不确定结果都不能默认为成功。

6. 人保留最终权

Human 可以 query、pause、interrupt、revise、accept、reject；accept 不包含 merge API。

Graph Runtime 的路由逻辑

implement
   │
   ▼
verifier ── passed ──► next verifier / review
   │
   ├─ failed ──► repair ──► verifier（受 repair budget 限制）
   │
   └─ error ──► retry / terminal error（不修改代码）

review ── succeeded ──► delivery
   │
   └─ failed ──► review_fix ──► fresh review / verifier

路由条件是受限数据（字段枚举 + 操作符），不是任意 Python 表达式；因此图可静态校验、序列化、hash 和审计。

存储设计

SQLite StateStore

Run、Node、Attempt、Contract、Conversation、Session、Verifier、External Handle、Review、Delivery 等可恢复状态；migration 单调升级。

JSONL EventStore

追加式事件与事务 outbox，便于时间线、审计和恢复诊断；它不是替代 SQLite 的状态源。

ArtifactStore

stdout/stderr、diff、测试、报告和原始 provider 输出按 sha256 内容寻址，报告只引用不可变 artifact。

Git Worktree

每个 Run 独立 branch/worktree；accepted commit 物化，但 Human 不会被系统自动 merge。

项目缺陷与取舍

  • 抽象领先于接线：协议、Verifier 和 Runtime 很完整，但主路径仍偏工程原型。
  • SQLite 单机权威：换来可审计和快速迭代，代价是没有多机 HA、远程 worker 和多租户。
  • 规则 Intent Compiler：控制动作确定、可审计、fail closed，但复杂自然语言鲁棒性有限。
  • 安全依赖部署：allowlist 和 container policy 能收紧边界，但最终隔离仍受 OS、runtime 和权限影响。
  • 证据不是宣传：测试通过只能证明测试范围内的语义，不能替换真实 provider 资格。

面试高频问答

点击问题展开。回答顺序建议：先结论，再机制，最后承认权衡。

结论：普通框架关注如何组织 LLM 调用；Graph Engineering 关注自治开发的控制正确性。这里图有持久状态、Contract freeze、失败语义、Human barrier、证据和恢复，模型只占其中的推理节点。
结论：模型适合理解需求和生成代码，但不适合作为状态数据库或权限裁判。状态迁移、预算、验收、屏障和幂等必须由确定性 Runtime 决定，否则 Agent 可能修改自己的验收条件，或者把环境错误当成代码错误。
结论：failed 表示业务/验收不满足，进入 repair；error 表示 timeout、网络、进程或 provider 故障，按 retryable 和预算重试或终止。两者分开是为了不让 Agent 为 CI 抖动修改正确代码。
结论：外部触发前后写 checkpoint，使用稳定 idempotency key，恢复时先查询已有 handle；如果发现“可能已触发但没有 handle”，系统停止并在报告披露 unknown effect，而不是盲目重试。
结论：类型层强制 read-only，Reviewer 使用 fresh Session，输入只有 frozen Contract、diff 和客观证据，没有实现对话；输出只能是 approved、changes_requested 或 blocked。修复后必须重新验证并 fresh review。
结论：查询走独立 Observer/Reporter，只读 State/Event/Artifact/Git；查询前后检查 execution fingerprint，发现执行面变化就报隔离错误。Human Gateway 也不会把普通 query 转进 Implementer Session。
结论：merge 是不可逆的产品决策。系统负责实现、验证、审查和证据交付，Human 的 accept 只记录“我接受了”，没有 merge API，默认不改变主干。
诚实回答：控制层内核已经完整，但产品接线还不够完整：正式自治入口仍使用 deterministic fixture，Discovery 动态追问和按复杂度自动选图还未接上，真实 provider 与跨平台资格也需要授权环境。下一步优先完成真实闭环，而不是继续堆概念。

最后收束

自然语言先落库 → 意图确定性编译 → Discovery 形成 Contract → Human 冻结 → Graph Runtime 编排 → Verifier/Reviewer 反馈 → checkpoint 恢复 → Evidence/Report 交付 → Human 最终验收。
这条链路回答了一个问题：如何让 AI Coding 从“一次模型调用”变成“可控制的软件工程系统”。
