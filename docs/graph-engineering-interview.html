一句话定位

不是造 Agent，而是造 Agent 之上的「控制层」——把「需要模型推理的事」和「必须确定可靠的事」彻底分开。

Graph Engineering 是一个面向自治软件开发的图工程控制层：Human 用自然语言说清楚「要做什么、怎么验收、边界在哪」，剩下的「探索、方案设计、编码、测试、独立审查、证据交付」由确定性 Graph Runtime 编排多个受限 Agent 自动完成；Human 随时能无干扰地看进度、打断、改方向，最后自己拍板要不要合入。

一句话区分度：别的工具帮你「写代码」，Graph Engineering 帮你「管住写代码的一整条流水线，并且每一步都可恢复、可审计、可叫停」。

背景动机：传统 Coding Agent 为什么在长任务上失控

传统 Coding Agent 通常围绕一次长会话工作。复杂任务容易遇到五类失控（这正是本项目要解决的问题）：

失控点表现本项目的对策
需求只在聊天记录里上下文 compact 后需求、验收条件丢失需求落库为冻结的 TaskContract，append-only
Agent 自测自审既当运动员又当裁判，可能改测试让错误实现通过Implementer / Verifier / Reviewer 职责隔离 + 只读 Session
中断/恢复不可靠失败后分不清「重试/修代码/重跑基础设施/终止」持久化 checkpoint + 幂等键 + 失败语义分类
查询污染执行Human 查进度会打断/污染正在跑的 Agent独立只读 Observer，指纹校验非干扰
换 CLI 状态即失任务状态绑定某个工具会话，迁移即丢权威状态只在 SQLite，入口都是薄的

本质洞察（项目灵魂）：模型上下文是临时缓存，不是数据库。传统 Agent 把「推理」和「控制」混在同一个聊天会话里——需求在聊天里、状态在模型上下文里、验收标准可能被 Agent 自己改。本项目把这两类事分开，让「推理走模型、控制走确定性代码」。

Harness → Loop → Graph：项目在业界概念中的定位

这是 2026 年 AI Coding 领域最火的递进框架（Peter Steinberger「Stop prompting coding agents — design loops that prompt them」；随后转向 Graph），本项目的设计理念与之对应：

Layer 1

Harness Engineering

保证单个 Agent 节点拥有正确的工具、权限、上下文。

对应本项目：为每个角色构建独立 Harness，限制工具与权限（workspace-write / read-only 沙箱）。

▼
Layer 2

Loop Engineering

用测试、审查、失败反馈让单个任务局部收敛。

对应本项目：测试失败→自动修复、审查失败→修改重验、异常→重试/终止。

▼
Layer 3

Graph Engineering

把多个 Agent、确定性工具、反馈循环、外部系统、人工边界组织成可组合、可恢复、可审计的执行图。

对应本项目：持久化执行图 + 条件路由 + Human-in-the-loop。

关键理解（面试加分点）：三层是递进吸收而非替代——Loop 没有死，它「退」成了 Graph 每个节点内部的运行机制；Graph 也没有取代 Harness，任何一层都仍需要 Harness 打底。项目同时覆盖三层：Harness（职责隔离的沙箱）、Loop（反馈闭环）、Graph（持久化执行图编排）。

端到端流程（一次需求的生命周期）

# 一条主数据流贯穿始终： 自然语言需求 └─ 落库为不可变 HumanMessage └─ IntentCompiler 编译成强类型 ControlIntent（fail-closed） └─ Discovery 需求探索（确定性预扫 + 动态追问到无缺失项） └─ 生成 Contract 草稿 → Human confirm → 冻结（append-only + acceptance_lock） └─ Designer/Compiler 按复杂度设计执行图（简单=单链 loop，复杂=graph） └─ RunPlanner 准备 Run（prepared，不等于执行） └─ ge run 显式启动 → GraphRuntime 跑图（真实 Codex 写代码） └─ implement → verify →(failed) repair ↺ → review →(changes) review_fix → fresh review → deliver └─ 十文件交付包 + 终态报告 └─ Human accept / reject / revise（默认不自动合并）

贯穿全程的两条暗线（任何时候都能用来理解任意一处代码）：

  1. 这一步是「推理」还是「控制」？ 推理走模型（Codex），控制走确定性代码（纯 Python 状态机 + SQLite）。
  2. 这一步会不会破坏某个 append-only / 只读 / 幂等不变量？ 会，就一定有对应机制防住。

关键不变量（贯穿全系统的「宪法」）

  • 权威状态只在 SQLite：入口（CLI/插件/UI）都是薄的，插件和 MCP Session 不含权威 Run 状态，永远不直接写 SQLite 或 worktree。
  • 自然语言只作为 HumanMessage 进入：Runtime 只接受强类型 ControlIntent，杜绝自然语言直接改执行状态。
  • 查询/状态/报告永远只读：只读意图在类型层隔离，不打断执行。
  • pause/interrupt 先建 barrier 再停：屏障生效后，任何新 Agent/Verifier/子进程/HTTP 调用/GitHub 写都不允许启动。
  • failed（业务失败）与 error（基础设施异常）始终分开：前者进修复循环，后者重试或终止，不误判。
  • secret 值永不进 prompt/日志/事件/报告/UI：只引用名称，值在执行时注入环境，且多形态脱敏。
  • 默认永不自动 merge：accept 只写验收记录，merge_performed 硬编码 False，系统没有 merge API。
  • 图是数据，不是代码：路由条件只能用三字段 + 四操作符，杜绝模型通过图注入可执行逻辑。

思想一：推理 vs 控制的彻底分离（项目灵魂）

整个系统的所有设计决策，都源自同一个判断：

「需要模型推理的事」交给 Coding Agent；「必须确定可靠的事」交给确定性 Runtime。
类别内容交给谁
推理看懂需求、写代码、读 diff 审查Coding Agent（Codex）
控制状态流转、失败分类、预算、中断、恢复、证据、交付确定性 Runtime（纯 Python 状态机 + SQLite，不含任何模型调用）

为什么要这样分？因为传统 Coding Agent 的失控，本质是把这两类事混在同一个聊天会话里。需求在聊天记录里、状态在模型上下文里、验收标准可能被 Agent 自己改、中断不可靠、换 CLI 状态就丢。

五类事实源，各司其职（不可互相替代）：

  • 需求事实 = TaskContract（冻结后 append-only，禁止替换）
  • 状态事实 = SQLite（权威，跨进程可恢复）
  • 事件事实 = JSONL（追加式，事务 outbox 保证不丢不重）
  • 证据事实 = ArtifactStore（内容寻址 sha256，不可篡改）
  • 代码事实 = Git worktree（每 Run 独立 branch）

这五类事实源各司其职、互不替代，是「权威状态在持久层、不在内存」的第一处体现。

思想二：单向依赖铁律（分层架构为什么长这样）

# 谁依赖谁，永远不反向。核心层不出现 codex 字样，换 Coding CLI 只动 adapter。 models（协议，最底层，不 import 任何内部模块） ↑ runtime/store · events · artifacts（持久化三件套） ↑ runtime/engine（调度大脑） ↑ compiler / conversation / discovery / contracts / executor / verifier / review / delivery（领域能力） ↑ adapters（Codex，最外层 provider 专属代码） ↑ cli.py / service / mcp_server（入口，都是薄的）

铁律：核心层不出现 codex 字样。 这意味着「换 Coding CLI，只动 adapter」——ExecutorProtocol 定义抽象边界，Codex 是第一个实现它的 adapter，未来接 Claude Code 等 provider 只需新增 adapter，核心 Runtime/存储/协议一律不动。

思想三：图是数据，不是代码（安全边界）

执行图由冻结契约确定性编译而来，图的形状可复现、可校验、可静态分析。最关键的设计是 RouteCondition：

# 路由条件只能用三字段 + 四操作符，注释明写 "it is data, never executable source code" RouteField = result.status | result.retryable | attempt.number RouteOperator = equals | not_equals | in | not_in

为什么这么「吝啬」？因为图可能由 Designer/模型产出。如果允许任意表达式（任意 Python/Shell），图本身就变成了注入面。用封闭枚举 + 四操作符，就把「方案（图）」锁死在可静态审计的数据形态——模型可以决定「先做 A 还是 B、失败回哪」，但不能塞进一行可执行代码。

反直觉但有深意：「图是数据」不是限制能力，而是把「自由」关进「可审计」的笼子。方案层获得了拓扑自由度（并行、回退、handoff），同时保持可复现、可 hash 校验、可跨语言序列化。

三个差异化（最能体现「做控制层而非堆 prompt」）

差异化 1：契约冻结 + append-only

Contract 是「需求事实源」。允许改契约 = 允许 Agent 自我定义需求 = 验收失去意义。所以：

  • 模型层校验：TaskContract 的 validator 强制 append-only（revision 1 不得 supersede、supersedes 必须指向更低 revision）。
  • 仓储层封死：replace_frozen 无论怎样都抛错——用代码宣示「替换契约」这个操作在系统里不存在。
  • hash 绑定：冻结时生成 acceptance_lock，把 Contract 与 Verifier 的 hash 绑在一起。

最狠的一处代码：replace_frozen 不是「暂未实现」，而是「永远拒绝」。append-only 不是文档写写，而是 API 层面就封死了。

差异化 2：failed 与 error 的失败语义分类

全项目最重要的判断：把「代码写错」和「环境抖了」在状态层分开。

状态含义应对
failed业务/验收未通过（代码写错了）进修复循环，值得让 Agent 改
error执行器/Verifier/基础设施异常（环境抖了）重试或终止，不默认改代码

为什么这是命门？因为如果 CI 网络抖动被判成「代码失败」，就会让 Implementer 去改一轮本来正确的代码，甚至引入新 bug。这条线贯穿一切：ExecutorResult/VerifierResult 的模型验证器强制 failed 和 error 不能混淆。

差异化 3：Human 正交控制面

Human 的查询、暂停、中断、修订，走一条与执行正交的通道：自然语言 → HumanMessage → ControlIntent → Runtime。查询走独立只读 Observer，不进入 Implementer/Reviewer/Verifier 的 Session，前后用 fingerprint() 校验「主 Run 状态没被污染」。

三句话总结设计哲学

  • 可恢复：事务化 checkpoint + 幂等键 + 不确定副作用「披露而非重试」。
  • 可审计：五类事实源各司其职，证据内容寻址，契约 append-only，图是数据。
  • 可叫停：pause/interrupt 先建 barrier 再停，任何新副作用都不允许在屏障后启动。
「自然语言先落库 → 确定性编译成意图 → 探索出契约 → 冻结 → 编译出图 → 状态机跑图 → 编译出证据链 → 人拍板，永不自动合并。」

模块 1：协议层 models/ —— 强类型是地基▶

职责：定义整个系统的「协议」，36 个 Pydantic 模型导出为 JSON Schema，是跨语言/CLI 迁移的根基。

关键机制

  • ProtocolModel（common.py）：提供 canonical_json()（确定性序列化：排序键 + 紧凑分隔 + 排除 None）和 sha256()——这是「冻结证据」和「内容寻址」的根基。
  • TaskContract（contract.py）：validator 强制 append-only（revision 1 不得 supersede、supersedes.revision 必须更低、验收条件引用的 verifier 必须存在）。
  • ExecutionGraph / Node / Edge / RouteCondition（graph.py）：RouteCondition 注释「it is data, never executable source code」，只用 result.status / result.retryable / attempt.number 三字段 + equals/not_equals/in/not_in 四操作符。
  • HumanMessage / QueryControlIntent / StateChangeControlIntent（control.py）：用 intent_kind 判别联合把「只读查询」和「状态变更」在类型层隔离；QueryControlIntent.requires_confirmation 硬编码 Literal[False]。
  • ExecutorResult / VerifierResult（results.py）：validator 强制 failed 必须有 failure_reason/failure_details、error 必须有 error 对象——从类型上把「失败」和「异常」分开。
  • RunStatus / TerminalStatus（reports.py）：Run 状态 14 个（draft→awaiting_confirmation→running→pause_requested→quiescing→paused→delivery_ready→succeeded/failed/error/interrupted/cancelled/rejected）；终态 6 个（succeeded/failed/error/interrupted/cancelled/rejected）。FinalReport 强制「终态状态 ↔ 终态原因 ↔ error」一致。
# 查询意图的类型级只读：requires_confirmation 硬编码 Literal[False] class QueryControlIntent(ProtocolModel): intent_kind: Literal["query"] ... requires_confirmation: Literal[False] = False # 变更意图：restart 必须有 restart_from，action 与字段强一致 class StateChangeControlIntent(ProtocolModel): intent_kind: Literal["state_change"] ... requires_confirmation: bool @model_validator(mode="after") def action_specific_fields(self): if self.action is StateChangeAction.RESTART and self.restart_from is None: raise ValueError("restart_from is required for restart") ...

面试价值点：「协议即代码」——36 个 JSON Schema 从模型导出，并有 drift 测试保证协议稳定。「用类型系统把设计不变量物理化」，是最能体现设计成熟度的一句话。

模块 2：持久化 store/events/artifacts —— 状态机 + 事件溯源 + 内容寻址▶

职责：三层存储各司其职，让权威状态跨进程可恢复、事件不丢不重、证据不可篡改。

1. SQLite StateStore（store.py）

单调 migration（Phase 6 时 head=10，代码用一串 property 层层委派做版本兼容：schema_version → latest_migration_version → storage_migration_version → database_migration_version → delivery_migration_version → service_migration_version → parallel_migration_version → container_migration_version → autonomous_delivery_migration_version，最后一个直接 SELECT MAX(version) FROM schema_migrations）。

# 写事务：BEGIN IMMEDIATE 立即锁，异常回滚 @contextmanager def transaction(self) -> Iterator[sqlite3.Connection]: connection = self._connect() try: connection.execute("BEGIN IMMEDIATE") yield connection connection.commit() except BaseException: connection.rollback() raise

事件 outbox（事务性发件箱）：enqueue_event 把事件 JSON 写进 event_outbox 表，与状态变更同一事务——状态和它触发的事件要么一起提交、要么一起回滚。这是「事件不丢不重」的根基。读侧 read_connection() 用 mode=ro 只读连接 + 不写锁，写连接开启 WAL + synchronous=FULL。

2. JSONL EventStore（events.py）

def _flush_locked(self, state) -> int: existing = self._existing_ids() # 读已有 event_id 去重 delivered = 0 for row in state.outbox_rows(): event_id = str(row["event_id"]) if event_id not in existing: with self.path.open("a", ...) as stream: stream.write(str(row["event_json"])); stream.write("\n") stream.flush(); os.fsync(stream.fileno()) existing.add(event_id) state.mark_event_delivered(event_id) # 标记已投递 delivered += 1 return delivered

同一事件不会因重复 flush 而重复落盘：先读已有 id 去重，再追加 + fsync。

3. ArtifactStore（artifacts.py）—— 内容寻址

def put_bytes(self, content, ...) -> Artifact: digest = hashlib.sha256(content).hexdigest() relative = Path("sha256") / digest[:2] / digest # sha256/前2位/完整hash target = self.root / relative if target.exists(): if target.read_bytes() != content: raise RuntimeError("artifact digest collision") # 碰撞即抛错 else: temporary = target.with_name(f".tmp-{uuid.uuid4().hex}") with temporary.open("xb") as stream: stream.write(content); stream.flush() os.fsync(stream.fileno()) os.replace(temporary, target) # 原子落盘 return Artifact(artifact_id=f"sha256:{digest}", ...)

先写临时文件再 os.replace 原子落盘 + fsync；已存在则校验内容（碰撞即抛错）。SQLite 只存元数据，大日志不进库。read_bytes 还校验 URI 不逃逸 store 根目录（防路径穿越）。

为什么分三层：状态需要事务一致性（SQLite）、事件需要顺序追加（JSONL）、证据需要不可篡改（内容寻址）。三者职责不同，混在一起会互相拖累。

职责：把冻结的 Contract 编译为执行图。关键设计是图随需求复杂度伸缩，而不是所有需求都套同一张固定图。

复杂度信号 → 图模板

复杂度信号产出图
低复杂度（单验收条件、单验证器、无跨模块依赖）单链 loop：inspect → implement → verify ⇄ repair（无 review 回环）
中复杂度（多验证器、有审查价值）标准图：inspect → implement → verify… → review → deliver（含 review_fix 回环）
高复杂度（可并行分解、跨模块）并行图：inspect → {implement_a ‖ implement_b} → join → verify → review → deliver

为什么不能固定模板（面试深度点）：Harness→Loop→Graph 三层里，Loop 的精髓是「针对任务设计停止条件」，Graph 的精髓是「针对任务设计拓扑」。如果每次都走同一张 inspect→implement→verify→review→deliver 固定图，Loop 和 Graph 的精髓就丢了——退化成 Harness。所以设计上让 Designer/Compiler 依据契约的复杂度信号选择图模板，简单需求走单链、复杂需求才引入 graph，在「可审计的确定性」与「按需伸缩」之间取平衡。

无论哪种模板，图始终是「数据」：节点类型封闭枚举、路由条件只用三字段四操作符，可静态校验（ge graph validate）、可 hash 复现（graph_id 含 contract hash）。

阶段 1：自然语言进入系统 ——「先落库，再解释」

入口：ge start 交互式 REPL（或插件/MCP 的 message 工具）。

数据流转：输入一句话 → 构造不可变 HumanMessage → 先 append 落库 → 再解释。

关键不变量：消息永远先落库，再被解释。

# conversation/repository.py append() 的顺序 def append(conversation_id, message): # 1. 先校验 actor/project 一致 # 2. 幂等：同 message_id 重复则返回原消息，内容碰撞则抛错 # 3. 写入 human_messages 表（不可变） # 4. 才发 human.message.received 事件

为什么：如果解释失败、进程崩溃、后续处理出错，原始自然语言不能丢。这是「权威状态在持久层、不在内存」的第一处体现。

阶段 2：需求探索 ——「确定性澄清 + 动态追问」

入口：DiscoveryService，由 start 流程触发。

# discovery 流程 discovery.start() → ProjectScanner.scan() # 预扫仓库（确定性，列文件） → 生成首轮 unknown # 固定维度起手 → 逐项 next_question/answer # 多轮澄清 → 每轮只读仓库分析产出 missing_information → 转成新 unknown 继续追问 → 直到无缺失项（或 max_rounds 兜底）→ _draft() 规则拼 TaskContract

关键不变量：澄清主路径是确定性的；模型的只读分析只做「缺失项生成」，不改澄清的确定性。

为什么：需求澄清是「控制面」的一部分，需要确定、可审计、可复现；但「固定问 N 个问题就结束」会漏掉复杂需求的缺失项，所以用动态追问 + 上限兜底在两者间平衡。

阶段 3：契约冻结 ——「append-only 的真相」

入口：ContractRepository，用户在 confirm 后触发。

关键不变量：契约一旦冻结，只能追加新版本，不能修改或替换。

三层防线：

  1. freeze 必须先过 _confirmed（匹配 confirm/确认/同意/批准），否则抛错。
  2. apply_delta 强制「delta 必须作用于最新 frozen 版本」，新 revision 自动 supersedes 旧 revision。
  3. replace_frozen 无论怎样都抛错——「替换契约这个操作在系统里不存在」。

为什么这么狠：Contract 是「需求事实源」。如果实现 Agent 能改契约，「自治开发」就变成「Agent 自己定义需求然后自我满足」，验收失去意义。

阶段 4：图设计 ——「方案按复杂度伸缩，而非模型乱画」

入口：Designer/ExecutionGraphCompiler.compile。

关键不变量：执行图由冻结契约确定性编译而来，图随需求复杂度伸缩，但始终是数据不是代码。

# 三种图形态（按复杂度信号选择） 低复杂度 ──► 单链 loop： inspect → implement → verify ⇄ repair 中复杂度 ──► 标准 graph： inspect → implement → verify… → review → deliver ↺ review_fix ┐ 高复杂度 ──► 并行 graph： inspect → {implement_a ‖ implement_b} → join → verify → review → deliver

为什么不是模型自由生成：「方案」如果由模型自由生成，就有两重不可控：① 模型可能注入任意 Python/Shell 的图；② 图的形状不可审计。而「复杂度信号 + 模板选择」让「契约 → 图」这个映射可复现、可校验、可静态分析，同时避免了固定模板带来的「简单需求也要走完整流程」。

阶段 5：Run 准备 ——「图还没跑」

入口：RunPlanner.create。

数据流转：校验 acceptance lock 与契约一致 → compile 成图 → 写 planned_runs（status=prepared）→ 写 immutable 文件（contract.json / graph.json / acceptance.lock）。

关键不变量：准备 ≠ 执行。RunPlanner 只做「生成并落盘一张已编译的图 + 血缘关系」，不启动任何执行。真正执行由 Human 显式 ge run 触发——确认和执行是分离的显式动作，确认绝不静默启动副作用。

阶段 6：自治执行 —— GraphRuntime 主循环（最重要的部分）

入口：ge run <run-id> → GraphRuntime.run()。

# 主循环骨架 while ...: # 1. 已经是终态？ → 返回 # 2. paused？ → 返回 # 3. pause/interrupt 屏障？ → 安全点暂停或中断 # 4. 预算耗尽？ → 终态 failed(budget_exhausted) # 5. 取下一个 ready/running 节点 # 6. 启动 attempt → _invoke → _persist_result # 7. _route_result（条件路由，决定下一条边）

两个状态层：Run 状态描述 Human 控制和整体终态；Node 状态描述单个节点的局部工作。两者正交。

阶段 7：反馈闭环 ——「失败就修，修完重验，验完再审」

三类闭环，对应三个问题：

闭环触发机制
测试失败 → 自动修复verify 节点 failedrepair 节点 → 回到首个 verify（max_iterations 限次）
审查需变更 → 修复重验 → 全新审查review 节点 changes_requestedReviewFixCoordinator：review → fix + 重跑受影响 verifier → fresh review
基础设施异常 → 重试/终止verify 节点 error按 retryable 决定重试或终止，不修代码

两条铁律：① 修复后必须重跑受影响 Verifier，不能复用修复前结果；② 审查必须是全新 read-only Session，不能是 Implementer 自省。

阶段 8：中断与恢复 ——「可恢复的真相」

中断（barrier）：pause/interrupt 意图在同一事务写 barrier + status。屏障生效后，主循环顶部、_start_attempt、DurableExecutorRuntime、各 Verifier 入口、GitWorkspaceManager 五处拦截，任何新 Agent/Verifier/子进程/HTTP 调用/GitHub 写都不允许启动。

恢复三板斧：

  1. 事务 checkpoint：run/节点/边/artifact 快照落盘，带 graph_hash/contract_hash，恢复时校验 lineage 防篡改。
  2. 幂等键：外部触发用 run_id:node_id 幂等键，HTTP 触发带 Idempotency-Key；已完成 Session 靠 completed_outcome 直接返回不重跑。
  3. 不确定副作用「披露而非重试」：recover 发现「triggering 但无 handle」——不盲目重试，生成 UnverifiedItem + ExternalEffect 明确披露「副作用可能已发生、不可安全重试」。

最值得记住的设计哲学：在无法保证 exactly-once 的外部系统面前，诚实的「我不知道、我停下来了」优于假装确定的「我再试一次」。

阶段 9：交付与验收 ——「证据链 + 永不自动合并」

交付报告：从持久化事实确定性编译十文件 bundle，不依赖最后一个 Agent Session 是否还活着。

需求矩阵：每验收条件一行，映射六类证据；只有 immutable 或 sha256: 引用才被信任，否则 fail-closed 为 unverified。

验收：accept 只写 append-only 记录，merge_performed: False 硬编码——整个系统没有 merge API。「把代码合进主干」这个不可逆动作永远留在 Human 手里。reject/revise 产生新 contract revision + 新 Run lineage。

为什么所有终态（包括失败/中断/取消）都生成报告：中断/失败后，残留副作用、未验证项、能否继续/修订正是 Human 决策最需要的信息。

一、项目背景与定位

1.1 传统 Coding Agent 的失控

传统 Coding Agent 围绕一次长会话工作。复杂任务上会出现五类失控：

  • 需求只存在聊天记录里：上下文膨胀、compact 后需求与验收条件丢失。
  • Agent 同时承担实现、测试、审查：可能通过修改测试或验收脚本让错误实现通过。
  • 失败难以归因：分不清应该重试、修代码、重跑基础设施，还是终止。
  • 中断/恢复不可靠：Human 查进度会打断执行；失败或中断后缺少可交付的报告。
  • 换 CLI 状态即失：任务状态绑定某个工具会话，迁移即丢。

1.2 核心解法：推理与控制分离

本项目把「一次自治开发」建模为持久化执行图，由确定性的 Graph Runtime 管理状态、边界和证据，只有需要模型推理的节点才交给 Coding Agent（Codex）。

模型上下文是临时缓存，不是数据库。Git 是代码事实，Contract 是需求事实，Verifier 是验收事实，Artifact 是执行证据，Graph Runtime 是状态事实。

五类事实源各司其职、互不替代。这是整个项目的灵魂——理解了它，下面所有设计（契约冻结、failed/error 分离、意图 fail-closed、secret 只引用）都有同一个来源：「把推理交给模型，把控制交给确定性代码」。

二、三层递进：Harness → Loop → Graph

项目在 2026 年 AI Coding 领域的认知框架中的定位（Peter Steinberger「design loops that prompt them」→ 转向 Graph）：

  • Harness Engineering：保证单个 Agent 节点拥有正确的工具、权限、上下文。
  • Loop Engineering：用测试、审查、失败反馈让单个任务局部收敛。
  • Graph Engineering：把多 Agent、确定性工具、反馈循环、外部系统、人工边界组织成可组合、可恢复、可审计的执行图。

三层是递进吸收而非替代：Loop 没有死，它「退」成了 Graph 每个节点内部的运行机制；任何一层都需要 Harness 打底。本项目的三个差异化正是这三层的落点：

  1. 契约冻结 + append-only（Harness 层：需求事实不可被 Agent 改写）
  2. failed/error 失败语义分类（Loop 层：反馈闭环的正确性前提）
  3. Human 正交控制面（Graph 层：多 Agent + 人工边界被组织进可审计的图）

    connection = self._connect()
    try:
        connection.execute("BEGIN IMMEDIATE")   # 写事务：立即锁
        yield connection
        connection.commit()
    except BaseException:
        connection.rollback()
        raise

事件 outbox（事务性发件箱）：enqueue_event 把事件 JSON 写进 event_outbox 表，与状态变更同一事务——状态和它触发的事件要么一起提交、要么一起回滚，事件不丢不重。

5.3 ArtifactStore（artifacts.py）—— 内容寻址

def put_bytes(self, content, ...) -> Artifact:
    digest = hashlib.sha256(content).hexdigest()
    relative = Path("sha256") / digest[:2] / digest   # sha256/前2位/完整hash
    target = self.root / relative
    if target.exists():
        if target.read_bytes() != content:
            raise RuntimeError("artifact digest collision")  # 碰撞即抛错
    else:
        temporary = target.with_name(f".tmp-{uuid.uuid4().hex}")
        with temporary.open("xb") as stream:
            stream.write(content); stream.flush()
            os.fsync(stream.fileno())
        os.replace(temporary, target)            # 原子落盘
    return Artifact(artifact_id=f"sha256:{digest}", ...)

先写临时文件再 os.replace 原子落盘 + fsync；已存在则校验内容（碰撞即抛错）。SQLite 只存元数据，大日志不进库。read_bytes 还校验 URI 不逃逸 store 根目录。

七、反馈闭环（Loop 的落点）

  • 测试失败 → 自动修复：verify failed → repair → 回到首个 verify（max_iterations 限次）。
  • 审查需变更 → 修复重验 → 全新审查：review changes_requested → fix + 重跑受影响 verifier → fresh review。
  • 基础设施异常 → 重试/终止：error → 按 retryable 决定，不修代码。

两条铁律（防 Agent 自欺）：

  1. 修复后必须重跑受影响 Verifier，不能复用修复前结果。
  2. 审查必须是全新 read-only Session，不能是 Implementer 在原 Session 自省。

十、图设计与 Discovery（可伸缩的控制面）

10.1 图随需求复杂度伸缩

  • 低复杂度 → 单链 loop：inspect → implement → verify ⇄ repair（无 review 回环）。
  • 中复杂度 → 标准 graph：加 review + review_fix 回环。
  • 高复杂度 → 并行 graph：inspect → {implement_a ‖ implement_b} → join → verify → review → deliver。

复杂度信号来自契约（验收条件数、验证器数、跨模块依赖、是否有并发要求等），由确定性编译器选模板。图始终是数据，可静态校验、可 hash 复现。

10.2 Discovery 动态追问

确定性预扫（列文件，限 500 文件/2MB）+ 每轮只读仓库分析产出 missing_information → 转成未知项追问，直到无缺失项（max_rounds 兜底）。澄清主路径保持确定性可审计，模型只做「缺失项生成」。

十二、设计亮点与面试加分项

  • 契约冻结 + 失败分类 + 职责隔离三件套——「为什么不会失控」的答案。
  • 图是数据不是代码——安全边界，杜绝模型通过图注入可执行逻辑。
  • 无法 exactly-once 处「诚实披露而非猜测重试」——最值得记住的设计哲学。
  • 类型层把设计不变量物理化——查询只读、failed/error 分离、reviewer 只读，都在 Pydantic validator / __post_init__ 里。
  • 协议即代码——36 个 JSON Schema + drift 测试。
  • 四种等价入口，薄前端——CLI/插件/MCP/UI 共享同一 Human Gateway，权威状态只在 SQLite。
  • 可观测性非权威——telemetry 永不参与 routing/recovery，exporter 失败不影响 Runtime。

十三、一句话收束

「自然语言先落库 → 确定性编译成意图 → 探索出契约 → 冻结锁定事实 → 按复杂度编译出图 → 状态机跑图（失败/异常分开、屏障可停、checkpoint 可恢复、副作用披露不重试）→ 从持久化事实编译出证据链 → 人最后拍板，永不自动合并。」

其中每一环都在回答同一个问题：「把推理交给模型，把控制交给确定性代码」——在这个分离之上，系统才是可恢复、可审计、可叫停的。

按 8 大模块分组，每题含主问题 + 面试官可能的追加追问。回答遵循「先结论 → 再机制 → 再为什么」的结构。

模块 1：架构定位与设计思想

Q1：叫 Graph Engineering，和 LangGraph / 普通 Agent 编排框架有什么区别？▶

结论：LangGraph 等解决「把 LLM 调用组织成图」，节点是 LLM/工具，状态靠模型上下文/内存。本项目核心是自治开发的「控制层」：图是持久化执行图，Runtime 确定性（GraphRuntime 是同步串行调度器），只有 agent 节点调 LLM。

三个差异化：① 契约冻结（禁止替换）；② 失败语义分类（failed vs error）；③ Human 正交控制面（查询走独立 Observer）。

一句话：它们管「怎么让模型多步协作」，我管「怎么让多步协作可恢复、可审计、可叫停」。

Q2：Harness / Loop / Graph 三者的关系？为什么你说三层都覆盖了？▶

结论：三者是递进吸收，不是替代。Harness 管单个节点的工具/权限/上下文；Loop 管单个任务靠反馈收敛；Graph 管多 Agent + 工具 + 外部系统 + 人工边界的编排。

关键理解：Loop 没有死，它「退」成了 Graph 每个节点内部的运行机制（每个 agent 节点内部仍在自循环）；Graph 也没有取代 Harness，任何一层都需要 Harness 打底。

本项目落点：Harness=职责隔离的沙箱；Loop=测试失败→修复、审查失败→重验、异常→重试的反馈闭环；Graph=持久化执行图 + 条件路由 + Human-in-the-loop。

追加追问「固定流程是不是退化回 Harness？」——是，这正是我设计「图随复杂度伸缩」的原因：Loop 的精髓是任务相关的停止条件，Graph 的精髓是任务相关的拓扑。如果每次都走同一张固定图，Loop 和 Graph 的精髓就丢了。所以我让图按复杂度信号选择模板，简单走单链 loop，复杂才引入 graph。

Q3：为什么 Python + SQLite，不是 Go + Postgres？为什么单机串行？▶

结论：MVP 阶段化交付 + ADR 冻结决策。核心价值在「控制层的正确性设计」而非「高并发基础设施」，Python + SQLite 让状态机、协议、迁移快速迭代且可被任何人审计。

关键：SQLite 是权威单写者，天然契合「确定性 Runtime 串行调度」的模型；单机串行是 MVP 显式非目标（并行图是后续能力）。

追加追问「要不要上分布式」——分布式调度是明确的非目标，我不以替代 Temporal/Dagster 为目标；当前聚焦单机可控的自治开发闭环。

模块 2：持久化、恢复与一致性

Q4：进程崩溃后怎么不重复触发外部副作用（重复建 PR / 发 CI）？▶

结论：四层防线：

  1. checkpoint 时机：外部 handle 拿到后 / 结果写入后 / 路由前。
  2. 幂等键：外部触发用 run_id:node_id，HTTP 触发带 Idempotency-Key。
  3. 不确定状态显式处理：recover 发现「triggering 但 handle IS NULL」→ 披露而非重试。
  4. PR 幂等键：sha256(repo+run+base+head)，先 _discover 已有 PR 则 checkpoint；网络错误标 UNCERTAIN_EFFECT 拒绝盲重试。

一句话：无法 exactly-once 处，用「诚实披露 + 停止」而非「猜测重试」。

Q5：Human 查询进度为什么不污染 Coding Agent？怎么证明？▶

结论：四层隔离：① 读路径 mode=ro 只读连接；② Session 隔离（查询走独立 read-only Observer）；③ fingerprint 校验（查询前后 execution_fingerprint 不变，变了就抛 RoleIsolationError）；④ 成本隔离（Reporter 成本单独记录）。

证明：测试反复查询后 fingerprint 不变、executor.calls 为空、workspace 文件不变。

Q6：checkpoint 怎么防止恢复到被篡改的图？▶

结论：checkpoint 存 graph_hash/contract_hash，恢复时 _validate_run_lineage 校验一致否则拒绝；另有 FrozenInputs.verify 校验磁盘上 contract/graph/verifier/lock 四类文件 hash。

追加追问「hash 变了会怎样」——抛 FrozenInputMismatch / RecoveryError，fail-closed 拒绝恢复，绝不带着被篡改的图继续跑。

模块 3：Runtime 编排与反馈闭环

Q7：测试失败和测试跑不起来怎么区分？为什么这么重要？▶

结论：_node_status 把 Verifier 结果分类：failed→修复（代码错），error→重试/终止（环境抖）。

为什么：CI 网络抖动若当成代码失败，会让 Implementer 白改一轮正确代码甚至引入新 bug。HTTP Verifier 的 5xx 显式归类为可重试基础设施错误；Command Verifier 的 timeout 归 error 且 retryable=True。

一句话：「代码写错」和「环境抖了」需要完全不同的应对，这是反馈闭环正确性的前提。

Q8：修复循环怎么防死循环？▶

结论：三层预算：① 边级 max_iterations + edge_traversals 计数；② run 级 repair_iterations vs max_repair_iterations；③ node 级 max_repair_iterations/max_executor_calls/max_duration_seconds/max_cost_units。任一超限 → BUDGET_EXHAUSTED 终态。

Q9：条件路由为什么不用任意 Python 表达式？▶

结论：RouteCondition 是数据不是代码，只用三字段 + 四操作符。

三个理由：① 图可能由 Designer/模型产出，任意表达式 = 注入面；② 确定性、可静态校验；③ 可序列化为 JSON Schema。

模块 4：多 Agent 协作与 Harness（职责隔离/安全）

Q10：怎么保证 Reviewer 不「既当运动员又当裁判」甚至偷改代码？▶

结论：五层防线：

  1. 类型层：reviewer/observer 的 ExecutorRequest 强制 read-only。
  2. Session 层：should_rotate 对非 implementer 恒 True，每次 review 都 fresh。
  3. 输入隔离：ReviewContext 不含 conversation，Reviewer 只能看冻结 Contract + diff + 客观证据。
  4. 输出约束：Reviewer 不能改代码，只能 approved→deliver / changes_requested→fix→fresh review / blocked→stop。
  5. 冻结：验收 Verifier 对实现 Agent 只读，执行前 hash 校验。
Q11：secret 怎么防泄漏到日志 / prompt / 报告？▶

结论：四层：① 引用注入（secret 是「reference，never value」，值只在执行时注入环境）；② 多形态脱敏（raw/URL/base64/base64-urlsafe）；③ 流式脱敏（跨 chunk）；④ 全链路（进 Artifact 前 redact）。

一句话：值不进 prompt + 全形态脱敏 + 全链路兜底。

Q12：动态生成的 Verifier 本质是待执行代码，怎么保证安全？▶

诚实作答：有 manifest 能力白名单、argv-only、host allowlist、静态扫描 + 合约测试 + dry run、确认页展示行为摘要、冻结 hash 校验。

但明确承认：MVP 不能宣称动态代码「完全安全」，真正强隔离（容器）是后续项。容器 Verifier 已经做进系统（不可变镜像身份 + 默认拒绝网络 + 资源限额）。

加分点：「知道边界在哪」的坦诚比吹安全更得分。

模块 5：图设计与 Discovery（可伸缩的控制面）

Q13：执行图是怎么设计的？简单需求和复杂需求用同一张图吗？▶

结论：不是同一张图。图随需求复杂度伸缩：

  • 低复杂度 → 单链 loop（inspect → implement → verify ⇄ repair，无 review 回环）。
  • 中复杂度 → 标准 graph（加 review + review_fix 回环）。
  • 高复杂度 → 并行 graph（并行分支 + join）。

关键：复杂度信号来自契约（验收条件数、验证器数、跨模块依赖、是否有并发要求等），由确定性编译器选择模板，图始终是数据、可静态校验、可 hash 复现。

追加追问「为什么不让模型直接生成图」——模型自由生成图会带来注入风险和不可审计。我用「复杂度信号 + 确定性模板选择」在「可审计的确定性」和「按需伸缩」之间取平衡。

Q14：需求澄清是固定问几个问题吗？怎么保证复杂需求不漏问？▶

结论：不是固定问题数。是「确定性预扫 + 动态追问到无缺失项」：

  1. 确定性预扫仓库（列文件，限 500 文件/2MB）。
  2. 每轮只读仓库分析产出 missing_information（还有哪些测试/验收/权限/依赖/交付细节没澄清）。
  3. 把 missing_information 转成追问项，逐项澄清；每轮仍产生新缺失项就继续问，直到为空。
  4. max_rounds 上限兜底，防止死循环。

设计平衡：澄清主路径保持确定性可审计，模型只做「缺失项生成」，最终澄清动作仍确定、带上限。

模块 6：Human-in-the-loop 与交付

Q15：自然语言「暂停一下」怎么变成系统动作？意图判错怎么办？▶

流程：HumanMessage（不可变，先落库）→ IntentCompiler.compile → 强类型 ControlIntent → 确定性 Runtime 执行。

fail-closed：多动作/歧义/缺目标 Run → 不执行要求澄清；危险动作强制 requires_confirmation；置信度低于阈值不执行。

诚实点：当前是确定性规则匹配而非 LLM 分类——有意权衡（确定性、可审计、fail-closed），也是已知局限。

Q16：默认不自动合并，accept 到底做了什么？▶

结论：accept 只写 append-only HumanAcceptanceRecord，merge_performed 硬编码 False。整个系统没有 merge API。

产品哲学：不可逆的「合进主干」永远留给 Human。系统只负责「实现 + 验证 + 审查 + 产出证据」。

Q17：所有终态都生成报告，包括失败/中断/取消？为什么？▶

结论：是。6 个终态（succeeded/failed/error/interrupted/cancelled/rejected）都生成 FinalReport。

为什么：中断/失败后，残留副作用、未验证项、能否继续/修订正是 Human 决策最需要的信息。报告从持久化事实确定性编译，不依赖最后一个 Agent Session。

模块 7：工程质量与测试

Q18：怎么保证改动不破坏之前阶段？▶

结论：阶段化 + 基线 + 分层测试 + 协议稳定 + 静态检查。全量 244 测试（Phase 6F），mypy strict + Ruff，36 个 JSON Schema drift 测试。

分层：单元（状态机/路由/意图编译/secret 脱敏/hash 冻结）→ 集成（Fake Executor 完整图/修复循环/中断恢复/防重复触发）→ E2E（真实 Codex 受限任务）。

Q19：真实 Codex / 真实 GitHub E2E 做了吗？▶

诚实：真实 Codex 做了受限小任务 E2E；GitHub 用隔离本地 HTTP provider fixture 验证，文档明确标注「fixture 不冒充真实 E2E」。

加分点：「明确标出 unverified 项」本身就是「证据可信度分级」设计思想的体现——区分 deterministic fixture / real local / real external / blocked / unverified，绝不把 fixture 当真实证据。

模块 8：开放问题与反思

Q20：最大不足 / 重做会改什么？▶
  1. 意图编译是规则匹配，复杂自然语言不够鲁棒（下一步引入结构化 LLM 分类，保留 fail-closed + 置信度 + 确认策略）。
  2. Runtime 曾为 foreground/recoverable，现已加 Service/IPC/MCP 形成持久服务。
  3. 单机串行 → 已加并行图，但分布式调度仍是明确非目标。
  4. 动态 Verifier 安全边界——静态扫描 + 合约测试不是强隔离，容器 Verifier 已补上。
  5. 真实 GitHub/真实 collector E2E 受授权限制未全量验证。
Q21：最想强调的一个技术决策？▶

「契约冻结 + 失败语义分类 + 职责隔离」三件套。它是「为什么不会失控」的答案，最能体现「在做控制层而非堆 prompt」的设计成熟度。

升华：整个项目读通的标志，是能默念出那条主线——「自然语言先落库 → 确定性编译成意图 → 探索出契约 → 冻结 → 按复杂度编译出图 → 状态机跑图 → 编译出证据链 → 人拍板，永不自动合并」。每一环都在回答「把推理交给模型，把控制交给确定性代码」。
